# 紧凑表格：按列对齐识别，不再被并进段落

## Report

## [S1] Problem

`84525a8` 把识别结果合并成段落后，`e0c9e4b` 用「行内相邻框间隔 > 1.5 倍字高」
把表格行挑出来保持独立。实测 RapidOCR 对表格的真实分框行为：

| 列距 | 分框情况 | 现状输出 |
|---|---|---|
| 宽（≥110 px）| 每格一框，间隔大 | ✓ 逐行保留 |
| 紧（70–100 px）| **每格仍是一框**，但间隔 ≈ 1 字高 | ✗ 被当正文并成一段 |
| 极紧（≤40 px）| 相邻格被引擎融成一框 | ✗ 并段（此类需版面模型，本期不做）|

紧���表格是常见场景（Excel 截图、网页表格默认列距），不能漏。

## [S2] Design

决策：用户未在限时内回复 Grill 问题；按工作流规则选取推荐项
**列对齐检测**，依据是引擎实测数据直接支持（单元格始终分框，x 起点跨行对齐），
且为纯文本逻辑、不引入模型。

### S2.1 列对齐判定

`merge_boxes` 现有流程：框 → 按纵向重叠归并成行 → 行内按 x 排序拼接。在拼接前
新增一步 `_find_table_rows(lines)`：

- 对每一行，取其**第 2 个及之后**各框的 `x0`（第 1 个框是行首，正文每行也有，
  不算列信号）。
- 两行视为「列对齐」：存在一对框，`|x0_a − x0_b| ≤ 0.5 × 字高`。
- 相邻两行列对齐即连成一个表格块；块内行数 ≥ 2 且至少有一行框数 ≥ 2 才算表格。
- 表格块内每行独立成行（与现有 `_has_wide_gap` 路径汇合，同一出口）。

### S2.2 不误伤正文与列表

- 正文行通常只有 1 个框（引擎按行合并），没有第 2 框 → 无列信号。
- 单列项目列表（每行一个短框）同理只有第 1 框 → 不触发。
- 正文被引擎切成两框的偶发情况：相邻行第 2 框 x0 随机，对齐概率低；且要求
  连续 2 行都对齐才成块，单行偶合不触发。

### S2.3 与现有大间隔判定的关系

`_has_wide_gap`（宽表）与列对齐（紧表）是**或**关系：命中任一即独立成行。
两者在 `merge_boxes` 内合并为一个 `structural` 标记集合，输出拼装逻辑不变。
